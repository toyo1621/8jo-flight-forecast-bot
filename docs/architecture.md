# Architecture

The forecast site is a static Pages application generated by a Python build. The runtime build fetches source data, evaluates forecasts, persists immutable prediction snapshots plus publication candidates, and renders HTML. The deploy job marks a candidate published only after checking the live artifact ID. The public site does not call BigQuery or external APIs from the browser.

Past date URLs are permanent archive pages. `build_static.py` reads immutable
prediction snapshots and publication state plus observed outcomes from BigQuery,
selects a published snapshot (or an explicitly legacy row) before each flight's
forecast valid time, and renders the public score,
actual outcome, and a deterministic retrospective. Missing outcomes remain explicitly
unconfirmed and are never converted to cancellations. An archive read failure stops the
build so a transient BigQuery problem cannot deploy a site that drops old URLs.
Rows created by the publication-aware pipeline carry a tracking marker; if their
publication record is missing, they are not silently treated as legacy. Only rows
created before publication tracking was introduced remain eligible as explicit legacy
records.

The snapshot keeps forecast generation time, per-source retrieval time, forecast valid
time, and publication confirmation time as separate fields. A build with zero forecast
days fails before writing the static artifact, so an outage cannot replace the last
published site with a successful-looking empty page.

## Dependency direction

```text
clients/open_meteo.py       HTTP + Open-Meteo response parsing
clients/typhoon_impact.py   HTTP + JMA impact response parsing
            |
            v
web_app.py                  orchestration, cache fallback, Flask adapter
            |
            +--> ensemble_evaluation.py  one predictor call per member
            |        |
            |        +--> ensemble_quality.py  model-separated summaries
            |        +--> forecast_engine.py   injected predictor
            |
            +--> build_static.py --> prediction_provenance.py --> BigQuery storage
```

`clients/` contains the external HTTP boundary and fixture-tested parsers. It does not know about Flask, the cache, or BigQuery.

`ensemble_evaluation.py` is the domain evaluation boundary. It receives already-fetched member weather and an injected predictor, retains model/member identity, and derives confidence, model median probability, and risk counts from the same immutable evaluation records. It does not perform HTTP, Flask, or BigQuery operations.

`ensemble_quality.py` only summarizes evaluation results. Models remain separate; the combined confidence is the worst available model result and never pools GFS and ECMWF members.

`web_app.py` coordinates fetching, cache fallback, typhoon adjustment, and presentation. Its compatibility functions delegate to the client and domain layers so existing callers can migrate incrementally.

BigQuery history reads use a small bounded TTL cache (`HISTORY_CACHE_TTL_SECONDS`, default
300 seconds) with explicit invalidation after writes. Forecast calculation can also receive
history as an injected value, which keeps fixture-based builds independent of BigQuery.

## Performance budget

The supported forecast window is 11 days, 3 flights, and at most 62 ensemble members per forecast time. The domain evaluation budget is therefore `11 * 3 * 62 = 2,046` predictor calls per static build. A build evaluates each member once; confidence and the GFS/ECMWF comparison rows reuse those results.

The member identifier is retained as `<model>:<member number>` at the API boundary. When a fixture or caller omits it, the domain layer assigns a deterministic per-input fallback identifier.
