# 収集結果の整合性

## 状態と日付

`flight_forecast/collection_outcomes.py`はネットワーク・DBを参照しない判定境界です。
Arrived/Cancelled/Returned/Divertedを確定結果として扱います。
Normal/Delayed/Conditional/EstimatedArrivalは未確定です。ただし妥当なactualArrivalTimeが
あり更新時刻以前の到着を裏付ける場合は運航を確定できます。欠航・引き返しとactualArrivalTimeが
同居する応答は矛盾として保留します。未知・型不正も実績へ保存しません。

実データでflightDateがないことを確認しました。dc:dateだけを運航日に使いません。
明示日付がない場合は、取得日時が更新日時〜dct:valid内にあり、最大2時間差、
3時刻が同じJST暦日、更新時刻が06:00以降という保守的な条件を使います。
これは運航日を保証する公式の専用フィールドではなく、制限付き推定です。
深夜・日付跨ぎの遅延便は自動確定できない場合があります。取得できない前日の結果を、
当日の応答で補完しません。時刻のみの深夜到着は推測せず保留します。

raw再処理は保存時のfetched_atを使います。現在時刻を使って過去rawの日付を変更しません。
通常収集は実行開始時に当日・前日を固定し1回のODPT取得から両日を照合します。
手動の対象日固定は`--date YYYY-MM-DD`。GitHubの「再実行」は新しい取得であり、
当時の入力の再処理ではありません。当時の再現には`--replay-run-id`を使用します。

## 保存

7つのnullable列を追加します: outcome_state/source/observed_at/raw_run_id/raw_status/date_basis/locked。
旧行のNULLはlegacyであり、確認なしにconfirmedへ移しません。
確定結果だけを本表へ入れるため、履歴ページで予定を「運航」と表示しません。
結果と気象は独立です。気象がない結果も保存し、既存の履歴抽出は風向・風速欠測を除外します。
公開済み予測スナップショットは変更しません。

MERGEは管理者保護を最優先し、古い時刻・同時刻の異なる結果は上書きしません。
同時刻・同結果で欠測気象を補充できる場合のみ再更新できます。
管理者訂正との競合はmaintenance_auditへraw参照付きで記録し、自動上書きしません。
保護は気象も含む行全体です。解除・公式訂正の採用は別途管理者レビューが必要です。

## 移行（承認後のみ）

1. 収集workflowを一時停止。現行SHAと対象テーブルのバックアップを保存。
2. SQLを生成してレビュー（このコマンドは接続も更新もしません）:

```bash
python -m flight_forecast.migrate_collection_outcomes --protect-owner-report
```

3. 承認後にのみ実行:

```bash
python -m flight_forecast.migrate_collection_outcomes --protect-owner-report --apply
```

既存のoutcome_audit_20260908_owner_reportを根拠に6便の状態を検証して保護します。
監査記録がない環境では`--protect-owner-report`を付けず、別の根拠を用意してください。
6便不一致時は停止し、statusや気象を推測して書き換えません。
通常collectorは既存テーブルの新列を自動追加しないため、未移行なら安全に失敗します。

4. 7列の存在、6便のstatusとoutcome_locked、他日の状態が未変更であることを確認。
5. テスト済みコードを公開して1回手動収集。監査競合・欠測・raw・Pagesの結果を照合。
6. 定期実行を再開。

## 監視と公開

収集日は同じrunでも日付別に集約します。partialとrun_failedは別です。
複数回で3便が揃った場合、書込み件数ではなく保存済みの確定便数で完了を確認します。
2026-09-09以降の監視はconfirmed/lockedのみ数え、それ以前はlegacyも集計します。
過去行を確定へ移したという意味ではありません。
21時前の当日部分取得は未到来扱い、実際の収集失敗は時刻によらず報告します。
翌日の初回収集・Pages定期更新でも前日未取得を確認します。GitHub遅延時は通知も遅れます。
レポートには日付・便ごとの結果/気象、管理者訂正との競合、26時間以上の未実行を含めます。
収集側の既存Issue通知を使用し、Pages側は独立実行のwarning・Summary・artifactを残します。

Pagesは既存の6時間ごとの生成に加え、収集成功後に再生成します。
承認済みの`actions: write`は独立したrepublish jobに限定し、収集jobへは与えません。
main上の収集成功時だけ既存Pages workflowを起動します。監視が過去日の不足を検出しても、
今回保存した結果は再公開します。掃除のみ・収集失敗・feature branchでは起動しません。
Pagesのテスト・Lint・データ品質・静的検証・公開確認はすべて既存経路を通します。
Pagesの監視失敗は予報公開を止めません。公開自体の品質ゲートは維持します。
GitHub全体が停止すると内部監視も停止します。管理者は毎朝Actionsの最新実行日時を確認し、
26時間以上空いていれば手動調査します。独立した外部heartbeatは今回追加していません。

## 障害・ロールバック

- ODPT障害: rawがあれば再処理。なければ欠測のまま通知。過去取得可能とは仮定しない。
- 気象障害: 結果のみ保存し、後の同じ/新しい確定観測で補充。NULLを0へ変えない。
- 保護との競合: maintenance_auditのraw_run_idを読み、解除せず管理者へ確認。
- 新コードに問題: まず収集を停止。7列と訂正記録は残す。旧collectorは保護を認識しないため再開しない。
- Pagesは前回公開を維持できる。収集停止中も監視警告を隠さない。
- DDLの巻戻しや結果削除は不要。結果の復元が必要な場合だけバックアップ・監査と照合して個別承認する。

## テストの仕様変更

従来の「3便・気象が全部揃わないと全件拒否」と「EstimatedArrivalは運航」の期待値を
今回の承認仕様に合わせて変更しています。テスト削除やskipによる回避はしていません。
再現fixtureは合成データです。実ODPT raw、SQLダンプ、認証情報はGitへ追加しません。
